## 1. 这是什么项目

`TF6000_ADS_DOTNET_V5_Samples` 是 Beckhoff(倍福)官方提供的 **TwinCAT ADS .NET 客户端/服务端** 示例集合。

**ADS（Automation Device Specification）** 是倍福 TwinCAT 系统内部/外部通信的协议，简单理解：

- TwinCAT PLC 运行时（Runtime）在某个 **AmsPort**（如 851）上暴露它的全局变量、方法；
- 你的 C# 程序作为 **ADS 客户端**，通过 **AmsNetId + AmsPort** 找到目标，然后按变量名/地址读写数据、订阅变化通知、调用 PLC 方法；
- 本机或局域网内的 **ADS 路由器（Router）** 负责把 ADS 报文转发到正确的目标（本机的是 TwinCAT 自带的路由服务）。

这个仓库用近 30 个独立的小项目，把 ADS 客户端库 `Beckhoff.TwinCAT.Ads` 的几乎每个功能点都单独演示了一遍，是目前最全的官方参考代码。

⚠️ **重要兼容性提示**：`ks_control` 目前是 **.NET Framework 4.6.1** 的老式 WPF 项目（`ks_control.csproj` 里 `TargetFrameworkVersion=v4.6.1`），而本示例仓库里：
- `BaseSamples` 和最新的 `WpfAdsSession` 用的是 **.NET 8 / .NET 10**，NuGet 包 `Beckhoff.TwinCAT.Ads` 版本是 **7.x**；
- 其余大部分（Router/Server/Docker 等）用 **.NET 8**，包版本是 **6.x**。

`Beckhoff.TwinCAT.Ads` 7.x 不支持 .NET Framework 4.6.1。所以在正式开发 `ks_control` 前，需要先做一个决定：

| 方案 | 说明 |
|---|---|
| **A. 升级 ks_control 为 .NET 8 SDK 风格 WPF 项目（推荐）** | 与本仓库 `BaseSamples`/`WpfAdsSession` 完全对齐，可以直接照抄代码和包版本，长期维护性最好 |
| B. 保持 .NET Framework 4.6.1，改用 `Beckhoff.TwinCAT.Ads` 6.x | 6.x 支持 net461，但 API 与最新示例略有差异，需要对照旧版本文档 |

建议采用方案 A。这个决定影响后续所有代码怎么抄，建议我们动手前先确认一下。

## 3. 核心概念速查表

在看代码之前，先认识这几个类/术语，几乎所有示例都在用：

| 概念 | 说明 |
|---|---|
| `AmsNetId` | 目标设备的"地址"，形如 `192.168.1.10.1.1`；本机是 `AmsNetId.Local` |
| `AmsPort` | 目标设备上具体某个"程序"的端口；PLC 运行时常见端口 **851**（第一个 PLC 实例），路由器是 **1**，SystemService 是 **10000** |
| `AdsClient` | 最底层客户端，同步/异步读写、创建变量句柄、调用方法、订阅通知 |
| `AdsSession` / `AdsConnection` | 比 `AdsClient` 更高一层的封装，自带断线重连、状态监控、统计信息，**WPF 应用更适合用这层** |
| Variable Handle（变量句柄） | 用符号名（如 `MAIN.nCounter`）向 PLC "登记"一次，换回一个 handle，之后用 handle 读写，避免每次都传字符串 |
| IndexGroup / IndexOffset | 更底层的"地址"访问方式，不用符号名，直接按内存区域+偏移读写（性能最高，但要自己维护地址） |
| Symbol / SymbolLoader | 把 PLC 的符号表（变量名、类型、结构体定义）加载到 .NET 端，可以按名字查、按类型自动序列化，还能做"动态符号树"（跟 TreeView 控件天然适配） |
| Notification（通知/订阅） | 让 PLC 在变量变化时主动推送给 .NET 端，而不用一直轮询；用完必须 `DeleteDeviceNotification`，否则内存/资源泄漏 |
| Sum Command | 把多个变量的读或写打包成一次 ADS 请求，减少网络往返，批量读写用它 |
| ADS Server | 反过来，让 .NET 程序自己"扮演"一个 PLC，被别的 ADS 客户端读写 |
| ADS Router | 负责把 ADS 报文路由到正确目标的中间层；本机装了 TwinCAT 就自带一个 |

## 5. 其它分类示例详解

### 5.1 ClientSamples（客户端完整应用）—— ★ ks_control 重点参考对象

- **WpfAdsSession**（`net10.0-windows`, WPF）—— **全仓库里和 ks_control 定位最接近的示例**，强烈建议整体阅读甚至借用架构：
  - 完整的连接/断开生命周期管理，连接状态和 PLC 状态用背景色实时显示；
  - 连接统计信息面板（重连次数、失败次数、错误率），还能手动"注入错误"测试重连逻辑；
  - 一个独立的**符号浏览器窗口**（`SymbolsWindow`），用 `TreeView` + `HierarchicalDataTemplate` 递归展示 PLC 的结构体/数组/指针类型 —— 这是"变量监控表格/树"这类上位机功能的现成范式。
- **AdsCli**（Console）—— 极简命令行读写工具，附带 Docker 打包，可作为"脚本/自动化测试用小工具"的参考。
- **AdsOverMqttApp**（Console）—— 不经过 ADS 路由器，走 MQTT 隧道连接 PLC，适合边缘/容器化场景，暂时和 ks_control 关系不大。

### 5.2 ServerSamples（把自己变成一个 PLC）

- **AdsServerSample**：`AdsServerConsoleApp`（后台服务，起两个 ADS Server 实例）+ `AdsServerTester`（WinForms 手动测试面板）。
- **AdsSymbolicServerSample**：进阶，从零构建带完整符号表/结构体/RPC 方法的"符号化 ADS 服务端"，附带用 `TcXaeMgmt` PowerShell 模块测试的完整脚本，是理解"符号系统内部长什么样"的最佳参考资料。
- 目前 `ks_control` 大概率只需要做**客户端**，这两个示例可以先跳过，除非以后需要让 `ks_control` 反过来对外暴露数据。

### 5.3 RouterSamples（自己托管一个 ADS 路由器）

- **AdsRouterConsoleApp** / **AdsRouterWpfApp**：用纯 .NET 实现一个跨平台、用户态的 ADS TCP 路由器（不需要装完整 TwinCAT），WPF 版本还演示了"把 WPF 窗口本身实现成 `ILogger`，日志实时刷到 ListBox"的写法，做日志面板时可以参考。
- **AdsRouterAndClientConsoleApp**：⚠️ 这个项目引用了仓库外部的 `AdsApiDotNetCore` 兄弟仓库（`ProjectReference` 指向不存在的相对路径），**无法独立编译**，跳过即可。
- 一般情况下你本机装了 TwinCAT 就自带路由器，这批示例属于"没有 TwinCAT 环境时的替代方案"，暂时不是 ks_control 的优先项。

### 5.4 ProviderSamples / AdsSecureSamples（高级/小众）

- **CustomSessionProvider**：用 MEF 插件机制自定义整套 ADS 会话/符号提供者，属于框架扩展级别的高级用法，短期内用不到。
- **AdsSecureConsoleApp**：ADS over TLS 加密连接，涉及证书、密码套件配置，只有当 `ks_control` 需要连接**不受信任的网络**上的 PLC 时才需要看。

### 5.5 DockerSamples / ManagementSamples

- **DockerSamples**：在 Linux/Docker 里搭一整套虚拟 TwinCAT 系统（路由器+服务端+客户端容器），用于 CI/测试环境，和 Windows 桌面版 `ks_control` 关系不大。
- **PwshBroadcastSearch**：在 C# 里内嵌 PowerShell SDK 调用 `TcXaeMgmt` 模块做设备广播搜索。如果以后 `ks_control` 要做"自动扫描局域网内 PLC"功能，这是一个可参考的思路（调用 PowerShell 而不是自己实现广播协议）。

## 6. 配套 PLC 工程（跑示例必需）

`Sources/BaseSamples/` 下有两个 PLC 工程文件夹，**不是 C# 代码**，是 TwinCAT XAE 的 PLC 工程：

- `TwinCAT_Demo_PLC/`：**已编译好、可直接下载运行**的版本（含 `_Boot` 启动镜像），`.sln` 里实际引用的就是它。
- `SamplePlc/`：源码版本，未被 `.sln` 引用，适合想自己在 TwinCAT XAE 里重新添加/编译的场景。

两者的任务都固定跑在 **AmsPort 851**，变量名（`MAIN.nCounter`、`MAIN.boolVal`、`MAIN.PLCArray`、`MAIN.fbMath` 等）和所有 BaseSamples 代码里硬编码的名字一一对应。

**要在本机跑通 BaseSamples，你需要：**
1. 安装 TwinCAT 3.1（Build 4024 或以上）的 XAE 开发环境；
2. 用 XAE 打开 `TwinCAT_Demo_PLC.tsproj`（或把 `SamplePlc` 加入新建的 XAE 解决方案）；
3. 激活配置并启动（Run）本机 PLC 运行时；
4. 确认端口 851 能正常访问后，再运行 C# 示例。

如果暂时没有 TwinCAT 环境，可以先只看代码理解 API 用法，不必急着搭 PLC 环境。

## 7. 常见坑（新手尤其要注意）

1. **结构体对齐（Pack）**：TC3 默认 8 字节对齐，TC2 是 1 字节对齐；C# 端 `[StructLayout(Pack=...)]` 必须和 PLC 端结构体的 Pack 设置一致，否则读出来的数据全部错位（`ReadWriteAnyType`、`WriteStruct` 里专门强调了这点）。
2. **通知（Notification）用完必须删除**：`AddDeviceNotification` 之后如果不调用 `DeleteDeviceNotification`，会一直占用 PLC 端资源，多次订阅不清理会导致连接异常。
3. **UI 线程封送**：ADS 的回调（通知、状态变化）不在 UI 线程上触发，WinForms 用 `SynchronizationContext.Post`，WPF 用 `Dispatcher.Invoke`/`Dispatcher.BeginInvoke`——`WPFConnectionObserver` 和 `WpfAdsSession` 都是这么处理的，ks_control 也必须照做，否则会抛"跨线程访问 UI 元素"的异常。
4. **`AdsClient` vs `AdsSession`**：简单一次性读写用 `AdsClient` 够了；但凡涉及"长期保持连接、自动重连、显示连接健康状态"（这基本就是 ks_control 的核心场景），优先用 `AdsSession`/`AdsConnection`，参考 `WpfAdsSession`。
5. **AmsPort 851 是"第一个 PLC 实例"的默认端口**，如果 PLC 工程里配了多个运行时或者不是默认配置，端口会不一样，连接前要在 TwinCAT 里确认实际端口号。
6. **自定义 ADS Server 端口范围**：如果以后 `ks_control` 需要反过来对外暴露 ADS Server，自定义端口必须落在 `25000–25999` 或 `26000–26999`，避免和倍福保留端口冲突。

## 8. 面向 ks_control 的建议学习路径

1. 先确认第 2 节里的**兼容性方案**（升级到 .NET 8 SDK 风格 WPF，还是留在 .NET Framework 4.6.1）。
2. 通读 `BaseSamples/ReadWriteFlag`（S01）—— 一个文件基本盖住了所有读写方式。
3. 精读 `BaseSamples/WPFConnectionObserver`（S40）—— 篇幅小，是 WPF + ADS 最小可运行范例。
4. 精读 `ClientSamples/WpfAdsSession` —— 这是最终形态的参考架构：连接管理、状态展示、符号浏览器，`ks_control` 的主窗口大概率会长成这个样子。
5. 按需查阅 `EventReading`（订阅通知）、`SumReadWrite`（批量读写）、`MethodCall`（调用 PLC 方法）—— 这三个是实际业务开发里最常用到的能力。
6. 需要"自己对外暴露数据"或"局域网设备发现"等功能时，再回头看 `ServerSamples` / `ManagementSamples`。
